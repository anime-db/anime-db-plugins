# animedb-wikidata

Официальный плагин-мост **[Wikidata](https://www.wikidata.org)** для AnimeDB. Версия 0.2.0
распознаёт ссылки записи, находит элемент Wikidata и заполняет только `externalUrls`
(`FillerInterface`, `getFillableFields()` = `['externalUrls']`).

## Что это и чем не является

Запись каталога, у которой среди источников только ссылки Кинопоиска и/или IMDb, ни с чем не
связывается: плагинов Кинопоиска и IMDb нет, а ни один плагин аниме-каталога такие ссылки не
распознаёт. У элемента тайтла в Wikidata бывают и IMDb/Кинопоиск, и id аниме-каталогов. Плагин
— мост для связывания: он заполняет только `externalUrls`, дальше цепочку ведёт штатное
насыщение хоста.

Плагин **не** источник метаданных и **не** плагин Кинопоиска или IMDb. Хост и контракт он не
меняет, SPARQL (WDQS) не использует, ключи API не нужны.

## Что делает плагин

- **Распознавание ссылок** (`resolveExternalId()`) — чистый разбор URL без сети и БД.
  - Если среди ссылок есть ссылка аниме-каталога, результат `null`: мост нужен только записям
    без аниме-ссылок. Каталоги — хосты строк таблицы источников с `catalog: true` (с `www.` или
    без), плюс Shikimori (`shikimori.io|one|org` с поддоменами) и World-Art (`world-art.ru`):
    в Wikidata у них нет свойств, поэтому они остаются списком в коде. Отказ хост не кэширует — появится аниме-ссылка, и
    мост для записи просто не сработает.
  - Иначе берётся первый подходящий вид по приоритету, внутри вида — первая ссылка в порядке
    `$urls`: `wikidata.org/wiki/Q…` (также `m.wikidata.org` и `/entity/Q…`), затем
    `imdb.com/title/tt…` (с `www.`/`m.`), затем `kinopoisk.ru/film/N` и `/series/N`.
- **`findById()`** принимает `Q…`, `imdb:tt…` и `kinopoisk:N`.
  1. `imdb:`/`kinopoisk:` → поиск `haswbstatement:P345=<id>` / `P2603=<id>`; ноль элементов или
     больше одного — `null`.
  2. Сущность (`wbgetentities`, `props=claims|labels|sitelinks/urls`, `languages=ja|en|ru`,
     `sitefilter=ruwiki|enwiki|jawiki`); редирект (слияние) разворачивается, id записи не меняется.
  3. Есть **P527** (has part(s)) → `null`: это сериал с частями, сезон угадать нельзя.
  4. Нет ни одной строки таблицы с `catalog: true` после отбора значений → `null`.
  5. `externalUrls` — все строки таблицы со значением после отбора плюс страница
     `https://www.wikidata.org/wiki/Q…`. `title` (нужен только DTO, в запись не попадает) — метка
     `ja` → `en` → `ru` → `Q…`.
  Сбой сети, 5xx и битый JSON — исключение, а не `null`.
- **`find()` всегда пуст.**
- **Клиент Wikidata** (`src/Http`): HTTPS, `User-Agent` с именем плагина, версией и адресом
  репозитория, `maxlag=5` в каждом запросе, запросы последовательно и не чаще 1 в секунду на весь
  плагин (лимитер между процессами на lock-файле в каталоге кэша плагина), без повторов внутри
  плагина. Два запроса: поиск элемента по свойству (`list=search`,
  `haswbstatement:P345=<id>`, для Кинопоиска `P2603`) и получение сущности (`wbgetentities`,
  `props=claims|labels|sitelinks/urls`). Ответ найденной сущности кэшируется на 24 часа в каталоге
  кэша плагина; результаты поиска и «не найдено» не кэшируются. «Не найдено» (а также несколько элементов на один
  ключ) — `null`; сбой сети, статус не 200, битый JSON, ошибка API, в том числе `maxlag`, —
  исключение, повтор — при следующем насыщении. Таймаут 10 с (`WikidataClient::TIMEOUT_SECONDS`)
  задаёт PSR-18-клиент хоста: через PSR-18 плагин сам его выставить не может.
  Поиск CirrusSearch отстаёт от правок Wikidata на минуты — для моста это не важно.

## Id плагина — ключ поиска, и он не меняется

Id записи — не id элемента, а ключ поиска: `Q…` (ссылка на Wikidata), `imdb:tt…` или
`kinopoisk:N`. `resolveExternalId()` — чистый разбор URL, превратить ссылку IMDb в `Q…` внутри
него нельзя. Хост кэширует результат первого связывания, поэтому id после первого связывания не
меняется: у записи, связанной через IMDb, он остаётся `imdb:tt…` навсегда, даже когда плагин
добавит ссылку на свою страницу Wikidata. `findById()` принимает все три формы. Уникальность `(plugin_id, external_id)` не ловит две записи одного тайтла, пришедшие
разными ключами, — для моста это не важно.

## Почему `find()` пуст и как привязать запись вручную

`FillerInterface` расширяет `SearchByPluginInterface`, поэтому `find()` обязан быть. Поиск по
названию среди элементов с MAL/AniDB почти ничего не находит, а в цепочке поиска при скане он мог
бы создать запись с японским названием и типом `TvAnime`. Привязать запись к элементу Wikidata
вручную можно иначе: вставить ссылку на `wikidata.org` в источники записи.

## Таблица источников

Какие ссылки отдаёт плагин, задаёт файл `resources/sources.json`, а не код: одна строка — один
источник. Поля строки: `name`; `property` (`P4086`) **или** `sitelink` (`ruwiki`) — ровно одно;
`url` — шаблон с `{id}` (у sitelink не задаётся: адрес берётся из ответа); `id` — регулярное
выражение допустимого значения (не подошло — значение пропускается); `catalog` — аниме-каталог;
`example` — пара `{"id": …, "url": …}`.

| Источник           | Свойство / sitelink | Каталог |
|--------------------|---------------------|---------|
| MyAnimeList        | P4086               | да      |
| AniDB              | P5646               | да      |
| Anime News Network | P1985               | да      |
| AniList            | P8729               | да      |
| allcinema          | P2465               | нет     |
| IMDb               | P345                | нет     |
| Кинопоиск          | P2603               | нет     |
| Официальный сайт   | P856 (только http(s)) | нет   |
| Википедия ru/en/ja | sitelink `ruwiki`, `enwiki`, `jawiki` | нет |

Своя страница Wikidata добавляется всегда и в таблицу не входит. Совпадение ссылки у нескольких
записей (статья Википедии на франшизу, Кинопоиск на сериал) — нормально, а не дубль.

Отбор значений свойства: ранг `deprecated` отбрасывается; если есть `preferred`, берутся только
они; **если значений всё ещё больше одного — свойство пропускается целиком** (у сериала бывает по
MAL-id на сезон, первый попавшийся был бы угадыванием); значение, не подошедшее под `id`,
пропускается. Для sitelink правило многозначности не применяется.

## Как добавить источник

1. Допишите строку в `resources/sources.json` вместе с `example`; код не меняется. Тест проверяет,
   что шаблон от `example.id` даёт ровно `example.url`.
2. Сверьте шаблон с formatter URL (P1630) свойства на Wikidata. Он берётся вручную, а не на лету:
   у свойства их бывает несколько (у P345 — девять), а шаблон должен проверяться тестом.
3. `catalog: true` — только для аниме-каталогов: такая строка участвует в правиле «нет каталога →
   `null`» и в отказе `resolveExternalId()` по хосту из `url`.
4. Поднимите `version` в `manifest.json` и положите в PR только изменения этого плагина.

## Известные ограничения

- **`null` окончательный до принудительного насыщения:** хост ставит записи `filled_at`, поэтому
  элемент, у которого связи появятся в Wikidata позже, будет подхвачен только принудительным
  насыщением.
- **Элемент с P527 даёт `null`.** Мост полезен в основном для полнометражных фильмов и
  односезонных сериалов: ссылка Кинопоиска или IMDb указывает на сериал целиком, а одиночные MAL и
  AniDB у элемента сериала — первого сезона. Лучше без ссылки, чем со ссылкой на чужой сезон.
- **Метаданных нет:** названия, описания и жанры плагин не заполняет.
- Ссылок Shikimori и World-Art нет: таких свойств в Wikidata нет. Плагин Shikimori сам узнаёт свой
  id из ссылки MAL.
- Две записи разных сезонов, у которых из ссылок только Кинопоиск на один сериал, получают один и
  тот же ключ `kinopoisk:N` и дадут ложный «возможный дубль» (`PotentialDuplicate`): конфликт
  возникает уже на связывании.

## Разработка

```bash
composer install   # контракт + PHPUnit для IDE, статического анализа и локальных тестов
composer test
```

Тесты не ходят в сеть. В `tests/Fixture/` лежат ответы Wikidata: поиск по `tt1568921` и по
`492366` (один элемент Q699835), поиск без результатов, сущности Q699835 (фильм, с `sitelinks`) и
Q22126305 (сериал с `P527`), урезанные до нужных свойств и меток; фикстуры «несколько элементов»,
редиректа и таблицы с Anime-Planet синтетические.
