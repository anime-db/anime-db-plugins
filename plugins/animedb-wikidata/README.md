# animedb-wikidata

Официальный плагин-мост **[Wikidata](https://www.wikidata.org)** для AnimeDB. Версия 0.1.0 — это
распознавание ссылок и клиент Wikidata, а не заполнение: `findById()` и `FillerInterface`
появятся в следующей версии.

## Что это и чем не является

Запись каталога, у которой среди источников только ссылки Кинопоиска и/или IMDb, ни с чем не
связывается: плагинов Кинопоиска и IMDb нет, а ни один плагин аниме-каталога такие ссылки не
распознаёт. У элемента тайтла в Wikidata бывают и IMDb/Кинопоиск, и id аниме-каталогов. Плагин
— мост для связывания: он будет заполнять только `externalUrls`, дальше цепочку ведёт штатное
насыщение хоста.

Плагин **не** источник метаданных и **не** плагин Кинопоиска или IMDb. Хост и контракт он не
меняет, SPARQL (WDQS) не использует, ключи API не нужны.

## Что делает версия 0.1.0

- **Распознавание ссылок** (`resolveExternalId()`) — чистый разбор URL без сети и БД.
  - Если среди ссылок есть ссылка MAL, AniDB, Shikimori, World-Art, ANN или AniList (по хосту:
    `myanimelist.net`, `anidb.net`, `shikimori.io|one|org` с поддоменами, `world-art.ru`,
    `animenewsnetwork.com`, `anilist.co`, кроме Shikimori — с `www.` или без), результат `null`:
    мост нужен только записям без аниме-ссылок. Отказ хост не кэширует — появится аниме-ссылка, и
    мост для записи просто не сработает.
  - Иначе берётся первый подходящий вид по приоритету, внутри вида — первая ссылка в порядке
    `$urls`: `wikidata.org/wiki/Q…` (также `m.wikidata.org` и `/entity/Q…`), затем
    `imdb.com/title/tt…` (с `www.`/`m.`), затем `kinopoisk.ru/film/N` и `/series/N`.
- **`find()` всегда пуст.**
- **Клиент Wikidata** (`src/Http`): HTTPS, `User-Agent` с именем плагина, версией и адресом
  репозитория, `maxlag=5` в каждом запросе, запросы последовательно и не чаще 1 в секунду на весь
  плагин (лимитер между процессами на lock-файле в каталоге кэша плагина), без повторов внутри
  плагина. Два запроса: поиск элемента по свойству (`list=search`,
  `haswbstatement:P345=<id>`, для Кинопоиска `P2603`) и получение сущности (`wbgetentities`,
  `props=claims|labels`, `languages=ja|en|ru`). «Не найдено» (а также несколько элементов на один
  ключ) — `null`; сбой сети, статус не 200, битый JSON, ошибка API, в том числе `maxlag`, —
  исключение, повтор — при следующем насыщении. Таймаут 10 с (`WikidataClient::TIMEOUT_SECONDS`)
  задаёт PSR-18-клиент хоста: через PSR-18 плагин сам его выставить не может.
  Поиск CirrusSearch отстаёт от правок Wikidata на минуты — для моста это не важно.

## Id плагина — ключ поиска, и он не меняется

Id записи — не id элемента, а ключ поиска: `Q…` (ссылка на Wikidata), `imdb:tt…` или
`kinopoisk:N`. `resolveExternalId()` — чистый разбор URL, превратить ссылку IMDb в `Q…` внутри
него нельзя. Хост кэширует результат первого связывания, поэтому id после первого связывания не
меняется: у записи, связанной через IMDb, он остаётся `imdb:tt…` навсегда, даже когда плагин
добавит ссылку на свою страницу Wikidata. `findById()` в следующей версии принимает все три
формы. Уникальность `(plugin_id, external_id)` не ловит две записи одного тайтла, пришедшие
разными ключами, — для моста это не важно.

## Почему `find()` пуст и как привязать запись вручную

`FillerInterface` расширяет `SearchByPluginInterface`, поэтому `find()` обязан быть. Поиск по
названию среди элементов с MAL/AniDB почти ничего не находит, а в цепочке поиска при скане он мог
бы создать запись с японским названием и типом `TvAnime`. Привязать запись к элементу Wikidata
вручную можно иначе: вставить ссылку на `wikidata.org` в источники записи.

## Известное ограничение

Две записи разных сезонов, у которых из ссылок только Кинопоиск на один сериал, получают один и
тот же ключ `kinopoisk:N` и дадут ложный «возможный дубль» (`PotentialDuplicate`): конфликт
возникает уже на связывании. Записи от Shikimori и World-Art несут собственные аниме-ссылки и до
Wikidata не доходят.

## Разработка

```bash
composer install   # контракт + PHPUnit для IDE, статического анализа и локальных тестов
composer test
```

Тесты не ходят в сеть. В `tests/Fixture/` лежат ответы Wikidata: поиск по `tt1568921` и по
`492366` (один элемент Q699835), поиск без результатов, сущности Q699835 (фильм) и Q22126305
(сериал с `P527`), урезанные до свойств P345, P2603, P4086, P5646, P1985, P8729, P527 и меток;
фикстура «несколько элементов» синтетическая.
